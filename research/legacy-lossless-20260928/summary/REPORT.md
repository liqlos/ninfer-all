## Контроль MMQ и fused gate/up — 30.09.2026

Отдельные сборки от `873d5e73` проверили две попытки ускорить фактический C4/MTP verification path без изменения весов. Принудительный J32 вместо J16 для Q4/Q6 ширины 9–16 прошёл 4×256 токенов, но одинаковый фиксированный seed дал batch wall 8,423 с у исходного ядра и 8,502 с у J32 (`results/profile-c4-seed-base-0930-requests.json`, `results/profile-c4-seed-j32-0930-requests.json`). В отдельном 2-секундном перекрывающемся окне CUPTI сумма Q4 MMQ снизилась с 1049,98 до 956,67 мс, Q6 MMQ с 362,13 до 349,91 мс, однако это сумма времен ядер, а не wall latency; J32 отклонён.

Прототип объединённого GGUF gate/up выполнил четыре запроса по 256 токенов без warmup. Два запуска исходного сервера заняли 9,148 и 9,201 с, прототипа — 9,427 и 9,553 с (`results/profile-base-c4-r{2,3}-0930-requests.json`, `results/profile-fused-c4-r{2,3}-0930-requests.json`). Выходы при том же seed расходятся и между запусками исходного сервера, поэтому текстовое сравнение не доказывает численную эквивалентность прототипа. Точный операторный тест не был собран: отдельный CMake-каталог требовал повторной компиляции 84 CUDA-объектов, а неконтролируемый параллелизм временно перегрузил WSL. Прототип не интегрирован.

Повтор без CUPTI (`profile_requests.py --no-trace`) отделил измерение задержки от профилирования: в порядке fused/base/fused/base batch wall составил 8,0065/8,3797/8,0494/7,6508 с при 1024 output tokens в каждом запуске (`results/profile-c4-notrace-{fused,base}-{a,b}-0930-requests.json`). Медианы практически равны: 8,028 с fused и 8,015 с baseline, а разброс baseline существенно больше разницы. Изолированный server и этот небольшой набор запросов не являются оценкой broker throughput; воспроизводимого C4 выигрыша здесь нет. Режим `--no-trace` не загружает CUPTI, прежнее поведение профилировщика осталось доступным по умолчанию.

Для следующего lossless-варианта критична геометрия: `target_verify_batch_impl` передаёт через слои `columns = width × batch`; при C4 и verification width4 это T16. Принятый paired-Q4 dispatch требует ровно T4 (`gguf_linear_q4_paired.cpp`), а Q6 field-vector dispatch заканчивается на T8 (`q4_paired_runtime_bridge.cu`). Следовательно, выигрыш этих vector-путей на C1 нельзя переносить на основной T16 bucket без отдельного MMQ layout, точной проверки и A/B. Это вывод из условий dispatch, а не измерение частоты T16 в текущей серии.

Сохранённый public-linked Q4 MMQ oracle v7 дополнен точными T16-прогонами на реальных полных матрицах с синтетическим Q8_1 входом (`results/q4-mmq-integrated-v7-t16-{gdn,down}-0930-t16-summary.json`). Пять graph samples, root/subviews и canaries подтвердили полный byte roundtrip, точные FP32/BF16 и graph replay. Медианы root raw→direct: GDN 0,097075→0,105779 мс (+8,704 мкс), down 0,104342→0,124416 мс (+20,074 мкс); unpack-then-raw намного медленнее (0,322253/0,337613 мс). Формат экономит 0,6075% байтов GDN и 0,5207% down. Даже оптимистичная пропорциональная оценка сокращения времени чтения при идеально memory-bound raw составляет только 0,590/0,543 мкс на операцию, соответственно в 14,8/37,0 раза меньше наблюдаемого штрафа direct. Активации являются настоящими Q8_1 захватами подходящей геометрии, но манифест не фиксирует слой: это proxy, а не доказанные входы `lm_head`. ## Научные основы и применимость собственного кодека — 30.09.2026

Сравнивать надо два разных результата: сколько исходных GGUF-байт можно убрать без потерь и уменьшает ли прямой decode внутри нужного NInfer-оператора время одного ответа. Простое уменьшение файла, выигрыш максимального batch и ускорение GEMM относительно другой библиотеки не доказывают последнее. Для Q4_K здесь 256 квантов занимают 128 B кодов и 16 B метаданных; у полного MLP-тензора H(code)=3,86874 из 4 bit, а H(code|scale)=3,86265. Значит, одни лишь частоты кодов оставляют примерно 4,20 B на 144-B блок; условие по scale добавляет всего 0,20 B до учёта таблиц, границ tiles и декодирования. Это ориентир нулевого порядка, не строгий предел для более сильного контекста.

| Энтропийный код с независимыми tiles | [Tile-ANS (ISCA 2026)](https://arxiv.org/html/2606.15789v1) подводит поток к энтропии, декодирует в shared memory и перекрывает GEMM; для их INT4 указано 0,6–1,0 bit/code. Дополнительный полный CPU scan `results/q4-cross-k-predictors.py`/`.json` (script SHA256 `1094412339d4888e98f63483bd749cf319cbea6d1f42837cae76ffd00930ee2e`, JSON SHA256 `232ed8915dfe80804bff144b8c1aade7d630bac9a3789b72124bf7764b44cbbc`) распаковал канонические Q4_K коды всех 83 886 080 GDN и 178 257 920 MLP весов. Соседние K-коды дали mutual information всего 0,006635/0,004548 bit/code; lag32/64/256 ≈0,000001–0,000002, тот же K соседней строки 0,000290/0,000003. XOR и mod16 residual имеют *большую* энтропию. После оплаты общей таблицы, 4-B row offset, до1-B row padding и32-B header идеальная оценка условного энтропийного кодера выигрывает у идеального безусловного лишь 69 289 B GDN и101 044 B MLP, или 0,147/0,101% от полных Q4 тензоров. Это не выпущенный codec и не реальный compressed size. Локальный row-codebook выигрывает по энтропии меньше стоимости индекса; последовательный контекстный decoder только добавил бы зависимость. Для этого нового предиктора GPU prototype отклонён по измеренному размерному gate; Q6-head здесь повторно не сканировался.

У собственного кодека есть смысл только после exact full-tensor proof для нового источника избыточности с оплаченной таблицей, индексом, padding и raw fallback. Затем нужен fused operator A/B на тех же активациях и FP32/BF16 byte-exact, включая CUDA Graph; только после выигрыша операции — paired C1. Для GDN T4 один accepted оператор уже читает 46,899,264 B logical coded weights за ~60,9 µs; его сокращение на 20% дало бы ~48,7 µs, ниже идеализированных 50,1 µs переноса этих же байт при паспортных 936 GB/s RTX 3090. Это **не измерение DRAM** и не доказательство невозможности: кэш, транзакции и перекрытие могут менять результат. Оно задаёт высокий порог для схемы, которая экономит всего несколько процентов веса. Аппаратный Blackwell Decompression Engine недоступен RTX 3090 ([NVIDIA FAQ](https://docs.nvidia.com/cuda/nvcomp/decompression_engine_faq.html)); GPU-кодек должен оплачивать decode на SM.
